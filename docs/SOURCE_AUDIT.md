# Source audit and migration decisions

## Repositories inspected

- Source investigation: [erneztox/artcam-investigation](https://github.com/erneztox/artcam-investigation), default branch `main`; recursive tree contained 1,302 files at audit time.
- New clean workspace: [erneztox/gravita](https://github.com/erneztox/gravita).
- Architecture decision: `docs/ARCHITECTURE_PIVOT.md`, approved 2026-11-11.

## Confirmed source facts

1. `crates/engine/src/cmd/generated_schemas.json` contains **116 command schema entries**. The complete exact JSON is preserved in [reference/source-command-schemas.json](reference/source-command-schemas.json); [COMMANDS.md](COMMANDS.md) renders each ID and field contract.
2. The old command module exports `bitmap`, `cam`, `common`, `doc`, `registry`, `relief`, `sim`, and `vector`. The presence of a module is not evidence that all its commands belong in the new product.
3. The old relief handler contains heightfield operations, relief-stack operations and mesh construction paths. The old CAM handler resolves imported vector entities into polygons/regions and computes toolpaths. The simulation handler creates a material stock heightfield and runs toolpath simulation, reporting removed volume, machined area, Z bounds, executed segments and collision state.
4. The old `xtask` dispatch includes `layers`, `panel-commands`, `parity`, `gui-parity`, `param-audit`, `stats`, and `ci`. Its `ci` sequence runs formatting, Clippy, workspace tests and the audits.
5. The old `parity` command reads the research menu inventory and compares it with CLI command output. The old `gui-parity` scans UI command references against the live engine registry. The old `param-audit` scans handler parameter access and GUI forms, generates the 116-entry schema and GUI parameter report. The old `layers` classifies crate dependencies and enforces layer boundaries. The old `panel-commands` lexes click-handler code to detect direct document mutation.
6. Old roadmap metrics and status claims are inconsistent: it claims CAM fully complete while also marking simulation in progress and desktop GUI planned; it reports historical WBS and command counts whose inventory scope predates the approved pivot. These numbers are not Gravita progress metrics.
7. At least one old UI README describes a vector/raster editor despite the approved pivot removing both. Documentation and code comments must be checked against the pivot before migration.

## Important design correction

The pivot document proposes an autonomous `gravita-geom` foundation and specific hand-built algorithms. The project requirement is instead to reuse mature Rust crates where they meet the need. Gravita will own stable domain types and adapters, not automatically reimplement offsets, booleans, Voronoi, BVH, raycasting or CAM algorithms. Each dependency decision must be backed by a recorded evaluation.

## Command inventory limitations

The 116 schemas are parameter contracts generated by lexical analysis of the old code. They do not by themselves establish full semantics, typed Rust payloads, transactional effects, safety guarantees, GUI/MCP parity, or acceptance. Some entries clearly conflict with the new scope (bitmap painting and interactive vector editing). Other entries are candidates, not automatically approved. Every retained ID needs handler-level inspection and a test trace.

## Migration policy

- Do not copy the old repository wholesale or preserve its Git history.
- Do not import old tests before classifying them against the pivot.
- Do not use the old README/ROADMAP percentages as current state.
- Preserve the exact command schema snapshot as research evidence, not as an API specification.
- Rebuild the typed command registry and programmatic Craft example as compiled clients of production APIs.
- Keep all excluded features explicit to prevent accidental scope creep.
